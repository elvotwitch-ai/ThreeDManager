## The defect

`SlicerName` was extracted with:

```
@"(?im)^\s*;\s*generated\s+(?:by|with)\s*(?<value>[^\r\n]+)"
```

`[^\r\n]+` greedily captures the whole rest of the line. PrusaSlicer, SuperSlicer, and OrcaSlicer
append the export timestamp to that line, so a real footer

```
; generated by PrusaSlicer 2.7.1 on 2026-07-15 at 10:00:00
```

was recorded as `PrusaSlicer 2.7.1 on 2026-07-15 at 10:00:00` — timestamp included. Because the
timestamp is unique per export, **the same slicer produced a different `SlicerName` for every file**,
so any future "group imports by slicer" report would treat each file as its own slicer. This finding
was flagged in `claude-admiring-sammet-692630.md` ("Findings the finalizer should not silently lose",
item 3) as belonging in its own trivial batch — this is that batch.

This is `docs/core/ROADMAP.md` Phase 1 "print imports" / `BACKLOG.md` Phase 1 "print import upload
and parsing" — the earliest incomplete phase. `docs/errors/errors.md` records no active bug, so no
filed bug outranked it.

## Why strip on the ISO date rather than after the version

The build timestamp always follows the form `on <YYYY-MM-DD> at <HH:MM:SS> [TZ]`. Anchoring the strip
on `\s+on\s+\d{4}-\d{2}-\d{2}\b` is unambiguous — no real slicer name or version contains an ISO date —
so the name and its full version (including `+win64`-style build suffixes, which precede the date) are
preserved and only the noise is removed. This is deliberately narrow: it does **not** strip on a bare
`" on "` or `" at "`, which could appear inside some legitimate generator string.

Slicers that carry no timestamp are provably untouched: Cura (`;Generated with Cura_SteamEngine 5.4.0`)
and the Creality line (`; Creality Print 5.0`) both pass `NormalizeSlicerName` unchanged, pinned by
`SlicerName_LeavesCuraUntouched_BecauseItHasNoTimestampSuffix` and
`SlicerName_LeavesTheCrealityLineUntouched`.

## Decisions taken autonomously (unattended run — flagging for review, not asking)

1. **Strip on the ISO date, not on `" on "`/`" at "`.** Narrow by design (see above) to avoid mangling a
   legitimate generator string that happens to contain those words.
2. **Version build suffixes are kept** (`PrusaSlicer 2.7.1+win64` stays intact) — they identify the
   build and precede the timestamp, so they are signal, not noise. Pinned by
   `SlicerName_KeepsTheVersionButDropsTheTimestampAndTimezone`.
3. **`ROADMAP.md` / `BACKLOG.md` deliberately not edited.** This fixes a defect inside the existing
   Phase 1 parsing line; it does not complete that line or move a phase.
4. **Not filed in `docs/errors/errors.md`.** That file tracks *active* errors; this one is fixed in the
   same commit that reports it. The finalizer's diary entry is the durable record.

## Findings the finalizer should not silently lose

1. **Historical `SlicerName` values already stored in `ParsedDataJson` still carry their timestamps.**
   This fix corrects new imports only; it does not backfill. As with the `FilamentUsedMeters` finding,
   the column is display-only and drives no cost/stock figure, so no repair migration was written — a
   grouping report can normalize on read, or an operator-approved one-off cleanup can run later. Worth a
   decision, not an opportunistic UPDATE.
2. **`SlicerName` still keeps unusual trailing tokens that are not a build timestamp** (e.g. a custom
   comment a user appended after the version on the same line). Only the `on <ISO date>` shape is
   stripped. Not observed in real slicer output; left narrow on purpose. Its own batch if it ever
   surfaces.
